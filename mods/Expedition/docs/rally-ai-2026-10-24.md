## Evidence and reason for this change

The latest local Fields/Dunes logs show no supported allies (`allies=0`) and no native/manual yields. Therefore those logs do not prove an ally map-order handoff problem. They do show enemies repeatedly receiving recovery destinations on alternate sides of almost the same spawn, and long intervals with no search/engagement while orders remain unchanged. A reported invisible/off-map shooter remains unconfirmed; the coordinator's separate native battle-area/spawn work addresses boundary rejection, not rendering.

The former ally default was to follow positions behind the player. Enemies approached the player's initial position, then could search random rings as large as 175 m. Both are replaced with the explicit requested opening: each AI team advances toward the other team's actual battle-start spawn center.

## Final AI behavior

- Each real hull's position is recorded once, at its first running-roster observation, before this controller gives it a move order. Both starting centroids freeze once expected spawns are observed; a two-second partial fallback can use existing actual observations, but never invent a missing side. Later hidden movement, casualties and control transfer do not update these spawn centers.
- Friendly AI rallies toward the enemy spawn center; enemy AI rallies toward the friendly spawn center. Their nominal slots have 24 m separation and finish 18/42/66 m before the target depending on row. If a wide slot fails terrain/bounds checks, narrower distinct lanes are tried. Arrival is measured against the actual assigned slot.
- Each team has separate contact memory. Only its own current native sightings can replace its opening spawn destination. Current visible contacts retain the previous 60 m preference to prevent small range changes from redirecting the formation. Direct attack target selection remains visibility-only, with the existing assignment preference and engagement hysteresis. Both teams use native aggressive attack approach, aiming and firing.
- When no opponent is visible near a remembered contact/opposing spawn, the hull sweeps a short deterministic corridor through that location. Across twelve slots the nominal search endpoints stay within 70 m of the target; no random 70–175 m rings remain. This is a local directed search, not a full-map search or knowledge of hidden live tank positions.
- Movement recovery now measures progress toward the actual rally/search goal, not arbitrary hull displacement. A slow hull gets eighteen seconds to turn/accelerate; going sideways without closing the goal does not reset that clock. Recovery requests a short native waypoint approximately 45 m forward and 16/20 m sideways, rather than 8 m forward and 25/35 m sideways. Its execution window is twenty-four seconds; returning to the main goal grants a fresh eighteen-second turning window. Rejected terrain/edge detours are also throttled, avoiding rapid reissuance of the unchanged goal. This asks the native pathfinder to recover; it cannot guarantee a route exists.
- `CampaignBattleArea.Contains(hit.point, 16f)` is required for every custom rally/search/recovery endpoint. This uses the coordinator's verified native battle-area capture. If no native area can be qualified, the optional controller explicitly releases claims and falls back to native map AI for this encounter. It does not suppress map orders while rejecting every custom waypoint.

## Native player commands and formation research

The current interop and native callsites verify this reference-only ingress:

`VehicleOrderConstruction.SelectConstructAndApply(IVehicleBehaviour sender, IOrderFactory[] orders, List<IOrderReceiver> receivers, IRadioOperator radioOperator)`.

Native `CommandSingleAsync` fills its receiver list with the selected receiver before this call; `CommandTeamAsync` fills its list via `GetRecieversInRange` before the same call. An observer prefix accepts only a real current player-controlled sender, a running owned Expedition battle and actual friendly receivers from that battle. Those specific receivers are handed back to native AI before command construction/application, including a command issued before the first automatic claim. No native task, return value or UI input is intercepted or cancelled.

This replaces the earlier broad rule that every external ally order caused permanent yielding. Autonomous allies now suppress map/formation orders just like autonomous enemies; a native player command selection or player control handoff releases only the relevant ally for the rest of that battle. Conservative limitation: cancelling command selection still leaves those selected receivers on native/manual AI for the battle. Commands issued solely by an unrelated mod do not have the verified vanilla-player ingress and are not assumed to be human orders. Normal modes outside Expedition remain untouched.

The existing formation guard was examined rather than changed on suspicion. In the current native binary `CommanderAI.MoveToPosition` (RVA 0x2019e10) directly constructs a `MoveToPositionTask` and inserts it into the driver's task queue; it does not call `UpdateFormationTasks`. The latter (RVA 0x20187b0) constructs separate tasks from formation state/cancellation. There is no evidence that suppressing formation updates blocks execution of our one-off move task. No value-type/byref/async-state-machine Harmony hook was introduced. The new observer has reference arguments only.

Local-only original snapshots, metadata and disassembly are in `artifacts/rally-ai-20261024-before`; they must not enter external model context or distributable packages. Installed GameAssembly SHA256 remains the verified `3E58082804D97CF32FFD400E7427E767EF9576D23DB71B2BE96FBB7F825FC17B`.
